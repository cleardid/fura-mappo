# FURA-MAPPO 项目总体要求

## 1. 项目定义

- 项目名称：FURA-MAPPO
- 仓库：`https://github.com/cleardid/fura-mappo`
- 开发分支：`main`
- 研究定位：独立建立的预测引导、不确定性感知多智能体主动资源预置系统，不依赖指定原文的隐藏代码或未公开实验细节。

## 2. 总体研究目标

在非平稳时空需求下，研究未来需求预测和预测不确定性对多智能体资源预置决策的价值。系统需要回答：

1. 真实未来信息相对于纯反应式方法是否存在可测量的控制价值？
2. 这种价值在何种需求非平稳性、资源稀缺度和服务约束下出现？
3. 预测误差、概率校准和不确定性质量如何影响控制收益？
4. 预测引导的 MAPPO 是否能在分布内接近 Oracle，并在分布外保持稳健？
5. 能否形成预测质量、需求变化速度和资源条件到策略收益的相图？

## 3. 科学门槛

### 3.1 未来信息价值门槛

在训练预测器或强化学习策略之前，必须比较：

- 反应式资源分配；
- 使用真实未来需求的 Oracle 配置。

如果 Oracle 在合理实验条件下不能稳定改善主要指标，应优先检查问题设定、资源约束和评价指标，而不是继续增加模型复杂度。

### 3.2 解耦原则

需求生成、预测、环境动力学、资源配置策略和评价必须是可替换组件。需求过程必须是外生随机过程，不得读取：

- 智能体位置或数量；
- 策略动作；
- 奖励；
- 任务完成状态；
- 强化学习模型参数。

### 3.3 可复现性

- 所有随机组件使用独立 RNG；
- 每次正式实验记录完整配置、种子、Commit 和环境；
- 统计比较优先使用配对随机种子；
- ID/OOD 边界必须在查看最终结果前冻结；
- 不得通过删除失败种子或任意放宽容差修饰结果。

## 4. 需求生成器要求

WP-01 最终必须支持：

- 平稳 Poisson 基线；
- Drifting Hotspot；
- Markov Switching；
- Burst Demand；
- 分布内和分布外参数区间；
- 可复现轨迹；
- 后续概率预测数据生成；
- 后续统计汇总、序列化和可选可视化。

WP-01 拆分：

- WP-01A：数据结构、公共接口、平稳 Poisson 和最小工厂；
- WP-01B：三类非平稳需求；
- WP-01C：配置、序列化、CLI、统计汇总和可选可视化。

各子工作包必须按顺序完成，禁止提前夹带后续功能。

## 5. 后续系统能力

需求模块完成后，研究系统应逐步建立：

1. 资源和任务服务环境；
2. 反应式、静态和 Oracle 基线；
3. 需求预测和概率不确定性输出；
4. 预测引导与不确定性感知决策接口；
5. MAPPO 训练和评估；
6. ID/OOD、消融和相图实验；
7. 可复现实验记录与论文材料。

后续阶段编号和公共接口只有在对应设计审查后冻结。

## 6. 工程约束

- Python 3.11；
- 当前 WP-01 CPU-only；
- 不使用系统 Python 2.7；
- WP-01 不安装 PyTorch、不改 CUDA 和驱动；
- Mac 只做快速 CPU 测试；
- GPU 和大规模任务由用户在 A100 服务器明确启动；
- 代码标识符英文，说明和关键注释中文；
- 公共接口有类型标注和数组形状说明；
- 用户输入不用 `assert` 校验；
- 不使用可变默认参数；
- 大型数据、模型和日志不进入 GitHub。

## 7. 版本和协作约束

- 单人 `main-only`；
- 不创建功能分支或额外 worktree；
- PR 和 candidate 标签不是必需流程；
- Codex 不执行 Commit、Push、Tag、Merge 或历史重写；
- 用户手工提交和推送；
- 服务器只从 GitHub 同步，不直接修改源码；
- 已推送错误通过追加修复 Commit 或 `git revert` 处理；
- 提交前使用完整补丁进行独立审查；
- 补丁只生成在 Desktop 或 Downloads，不使用 `/tmp`。

## 8. 质量门槛

每个工作包至少满足：

- 设计范围明确；
- 修改文件受控；
- 单元、边界和必要统计测试通过；
- Ruff 和格式检查通过；
- `git diff --check` 通过；
- 独立补丁审查无阻断问题；
- Mac 和服务器分别按规定验收；
- 状态、决策和交接文档真实更新。
